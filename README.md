# Verified Knowledge Agent

인수인계 문서가 없는 상태에서 서비스 운영을 맡았을 때,
**일할수록 도메인 지식이 쌓여 다음 대응이 빨라지는** AI 에이전트를 만들기 위한 프레임워크.

지식 저장소가 아니라 **지식이 쌓이고, 검증되고, 틀리면 격하되는 규칙 체계**다.
핵심 제약 하나 — *검증 절차를 쓸 수 없는 주장은 "확정"이 될 수 없다.*

---

## 왜 만들었나

운영을 인계받았는데 문서가 거의 없는 상황이 출발점이었다. 문제는 세 가지였다.

1. **같은 문의가 반복되는데 매번 처음부터 판다.** 지난주에 판 것과 같은 원인인데 기록이 없어 다시 추적한다.
2. **AI에게 물으면 그럴듯한 답이 나오는데 맞는지 알 수 없다.** 검증하지 않은 추정이 다음 대화에서 사실처럼 재인용된다.
3. **분석이 휘발된다.** 대화가 끝나면 사라지고, 담당자가 바뀌면 처음으로 돌아간다.

세 번째가 근본 문제고, 첫 번째는 증상이며, 두 번째는 순진하게 해결했을 때 생기는 부작용이다.
그냥 기록만 쌓으면 **틀린 기록이 사실로 굳는다.** 그래서 축적과 검증을 한 세트로 설계했다.

---

## 설계 원리

### 1. 소비 레인과 생산 레인을 나눈다
들어오는 일을 **즉답형(문의)** 과 **추적형(개선·분석)** 으로 먼저 가른다.

- 즉답형은 기존 지식을 **소비**한다. 목표는 속도.
- 추적형은 영역을 깊이 파므로 지식을 **생산**한다. 목표는 자산화.

추적형 한 건을 처리하면 그 영역의 다음 즉답형이 빨라진다. 복리 구조다.

### 2. "끝나면 사라지나, 남나"로 저장 위치를 가른다
진행 상황(커밋 해시, 잔여 작업)은 휘발성이고, 동작 방식(이 시스템이 어떻게 도는가)은 안정 지식이다.
섞어 두면 시간이 지나며 인용이 썩는다. 처음부터 다른 곳에 쓴다.

### 3. 모든 분석에 신뢰도를 붙인다
`가설` → `부분확인` → `확정` 세 단계.
**상태 표시가 없는 항목은 미검증으로 취급한다.** 절반짜리 분석이 사실로 둔갑하는 것을 막는 최소 장치다.

파일 단위 상태는 **그 안에서 가장 약한 주장** 기준으로 잡는다.
확정 파일의 후광이 그 안에 묻힌 가설에 씌워지면 안 되기 때문이다.

### 4. 확정에는 재실행 가능한 검증을 의무화한다 (핵심)
틀린 지식의 진짜 문제는 회수가 아니라 **탐지**다.
틀렸다는 걸 알아채는 게 운에 맡겨져 있으면, 회수 장치가 아무리 좋아도 틀린 확정이 영원히 서빙된다.

그래서 `확정`으로 올리려면 **`검증: <재실행 가능한 절차> / 기대: <값>`** 한 줄을 반드시 붙인다.
산문 근거가 아니라 다시 돌려볼 수 있는 형태여야 한다. 못 만들면 확정 금지, `부분확인`에 머문다.

이 한 줄이 세 가지 역할을 한다.
- **승격 게이트** — 검증 불가능한 주장이 확정으로 새는 것을 입구에서 차단
- **탐지** — 그 지식을 근거로 쓸 때 재실행해서 어긋남을 발견
- **신선도** — 코드가 그대로여도 데이터나 설정이 바뀌면 틀려지는 사실을 잡아냄

### 5. 쓸 때만 검증한다 (verify-on-use)
주기적 전수 감사는 하지 않는다.
**틀린 지식은 쓰일 때만 해를 끼치므로**, 검증 노력을 실제로 근거가 되는 지식에만 집중시킨다.
확정 사실이 답변의 근거가 될 때만 검증 줄을 재실행하고, 스쳐 지나가는 참조는 넘어간다.

### 6. 승격뿐 아니라 격하 경로를 만든다
올라가는 길만 있고 내려오는 길이 없으면 틀린 확정이 영원히 남는다.
반증을 발견하면 **지우지 말고 격하**한다.

- 상태를 `반증`으로 바꾸고, 틀린 주장에 취소선 + **왜 틀렸나** + **올바른 값**을 남긴다
  (네거티브 지식도 자산이다. 같은 오해의 재발을 막는다)
- 그 항목을 **직접 인용**한 문서를 한 홉만 찾아 재검토 대상으로 강등한다
- **재귀 전파는 하지 않는다.** 수십 개 규모에서 완전한 진리 유지 시스템은 과투자다

### 7. 위험도에 따라 자율 수준을 나눈다 (이층 게이트)
확인을 모든 곳에 두면 아무것도 안 쌓이고, 아무 데도 안 두면 사고가 난다.
**게이트는 위험한 곳에만 둔다.**

| | 예시 | 처리 |
|---|---|---|
| 낮은 위험 | 읽기·검색, 잠정 지식 저장, 티켓 등록, **틀린 확정의 격하** | 묻지 않고 자동 |
| 높은 위험 | **확정 승격**, 확정 항목 삭제, 커밋·배포, 운영 영향 | 실행 전 확인 |

격하가 자동인 이유는 신뢰를 **낮추는** 방향이라서다. 틀린 걸 사실로 두는 쪽이 더 위험하다.

### 8. 기계적 점검은 하네스에, 판단은 모델에
빠뜨림 여부처럼 규칙으로 확정되는 것은 훅과 스크립트로 강제한다.
분류와 검증처럼 맥락이 필요한 것만 모델이 판단한다. 모델에게 규칙 준수를 부탁하지 않는다.

### 9. 못 찾은 것도 기록한다 (miss loop)
지식에서 못 찾았을 때가 성장 지점이다.

1. 인덱스만 없는 건지, 실제로 존재하지 않는 건지 직접 확인한다
2. 있으면 → 영역 문서로 쌓는다. 다음엔 즉답
3. **없으면 → "없음"도 기록한다.** 같은 막다른 길을 다시 탐색하지 않기 위해

매번의 실패가 기반을 키운다.

## 구조

| 층 | 내용 | 위치 |
|---|---|---|
| **규칙** | 처리 순서, 분류 기준, 자율 수준, 금지 사항 | `AGENT.md` |
| **지식** | `deep/` 영역별 동작 분석과 진단 레시피, `qa-log/` 처리 기록, Layer 1 인덱스 | `.agent-context/` |
| **작업** | `tickets/` 추적 건, `_INFLIGHT.md` 병렬 세션 관제 보드 | `.agent-context/` |

### 진단 레시피
반복되는 증상은 정형화해서 쌓는다.

```
증상 → 확인할 데이터와 로그의 순서 → 자사 / 외부 책임 분기 → 검증 절차
```

같은 증상이 재발하면 처음부터 파지 않고 이 절차로 바로 시작한다.

### 병렬 세션 관제
문의마다 세션을 열어 병렬로 처리하면 세션끼리 서로를 모른다.
공용 보드 파일에 각자 한 줄씩 append하고, 세션 시작 훅이 그 보드를 자동으로 읽어 주입한다.
"보드를 읽는 걸 까먹어서 안 쓰이는" 문제를 자동화로 막는다.

## 사용법

```bash
./install.sh /path/to/project      # 프로젝트에 .agent-context 스캐폴딩 + 규칙 파일 배치
```

1. `AGENT.md`의 플레이스홀더(`{{PROJECT}}`, `{{REPOS}}` 등)를 프로젝트에 맞게 채운다
2. 첫 문의부터 그냥 처리한다. 지식은 처리하면서 쌓인다
3. Layer 1 인덱스는 초기에 한 번 생성하고, 큰 변경이 있을 때만 갱신한다

## 설계 노트

이 프레임워크의 판단 하나만 꼽으라면 **4번(확정에 재실행 가능한 검증 의무화)** 이다.

지식베이스를 만들면 보통 "쌓는 법"을 고민한다. 그런데 실제로 운영해 보면
**쌓는 것보다 쌓인 게 틀렸을 때가 훨씬 위험하다.** 검증되지 않은 추정이 문서에 박히면
다음부터는 그게 출발점이 되고, 그 위에 쌓인 분석까지 함께 오염된다.

그래서 "확정"이라는 라벨을 **자기 자신을 검증할 수 있는 형태로만** 붙이게 강제했다.
검증 절차를 못 쓰겠으면 그건 아직 확정이 아니라는 뜻이다.
이 제약 하나가 승격 게이트, 오류 탐지, 신선도 관리를 동시에 해결한다.
